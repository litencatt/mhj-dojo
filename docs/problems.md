# 練習問題の土台（#237）

何切る（#239）・押し引き（#241）・待ち当て（#242）と、CPU 対戦の振り返り（#238）は、どれも「局面を作り、エンジンの答えで採点する」形です。このページは、その共通の土台の設計です。道場の鍛錬では、秘伝の課題がこの土台に載ります。

## 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| 局面の作り方 | シードから決定的に作る（出題セットは同梱しない） | WASM も配る資産も増えない。問題は `kind`・`level`・`seed` の3つで決まるので、URL で共有・再現できる |
| 出題の質 | 生成した局面をフィルタで選ぶ。合わなければ同じシードから導いた次の候補を試す | シードからの決定性を保ったまま、「答えがはっきりした局面」だけを出せる |
| 状態 | 持たない。採点の要求は問題の id（`kind:level:seed`）を持ち、エンジンが局面を作り直して採点する | ストアもセーブも要らない。局面の生成は軽い（下の「性能」） |
| 正解 | 種類ごとの順位づけで1位に並ぶものはすべて正解 | 同率の手を不正解にしない |
| id | `kind:level:seed` をエンジンが書く形のままでだけ受け付ける（`01` や `+42` は 400）。シードは 0〜2^53−1 | ページが JavaScript の数として正確に読めるように。同じ問題に別の id ができないように |
| 答えを隠すか | 出題の応答に答えを含めない（採点の応答で初めて返す） | ページのコードから答えが見えないようにするため。秘密にする仕組みではない（エンジンは手元で動く） |

## 種類

| kind | 問い | 答え | 正解 | 局面の元 |
|---|---|---|---|---|
| `nanikiru` | 14枚から1枚切る | 牌1枚 | アドバイスの順位（向聴 → 有効牌 → 聴牌時の待ち、`docs/api.md` の Ranking 1〜3）で1位に並ぶ牌種 | 練習のセッションと同じ山で、アドバイスの最善を切り進めた途中の手 |
| `oshihiki` | 他家のリーチを受けて1枚切る | 牌1枚 | 手の中で危険度（`cpu.Danger` をリーチ者ごとに足したもの）が最も低い牌種 | CPU だけで打った対局で、他家がリーチしている間の自分の打牌 |
| `machi` | 聴牌形の待ちをすべて選ぶ | 牌種の集合（1〜9種） | 待ちの集合とちょうど同じ | 山から作った聴牌形、または清一色の多面張 |

振り返り（#238）は局面を生成しません。対局のセーブを再生して自分の打牌の局面を取り出し、`nanikiru`・`oshihiki` と同じ採点（`Grade`）を当てます。

この土台の最初の PR では `nanikiru` だけを実装し、残りは各 issue で同じ形に足します。`machi` は #242 で実装しました。

## エンジン（`internal/problem`）

```go
type Kind string // "nanikiru" | "oshihiki" | "machi"

type Problem struct {
	ID       string   // "nanikiru:1:12345": kind, level, seed
	Kind     Kind
	Level    int
	Seed     int64    // 求められたシード
	Source   int64    // 局面を作ったシード（フィルタで進んだ先）
	Position Position // 問題の局面（下）
	Choose   string   // "one" | "many"
	answer   answer   // 採点に使う。JSON には出さない
}

func Generate(kind Kind, level int, seed int64) (*Problem, error)
func Parse(id string) (Kind, int, int64, error)
func (p *Problem) Grade(answer []tile.Tile) (*Result, error) // 局面にない牌・枚数違いは ErrInvalid
```

- `Generate` は、`seed` から候補のシードを順に導き（`seed`、次に `wall.RoundSeed(seed, i)`、i = 1…`maxTries` = 100）、最初にフィルタを通った局面を返します。`maxTries` までに通らなければエラー（`ErrNoPosition`、要求では 422）です。シード 1〜2000 では、`nanikiru` はどの level も 31 番目まで、`machi` は 60 番目までの候補で見つかります。テストで、各 kind・level について決まった範囲のシードがすべて問題になることを確かめます。
- 局面（`Position`）は、ページが卓を描くのに要るものだけを持ちます。手牌（13枚と、ツモ牌がある問題ではツモ牌）、ドラ表示牌、巡目、場風・自風、自分の捨て牌、見えていない枚数（`remaining`、有効牌の数え方がセッションと同じになるように）。各家の捨て牌とリーチは `oshihiki` で足します。牌の表記は他の要求と同じです。
- `Grade` は答えの牌ごとの評価（順位・向聴・有効牌・危険度）と、正解の牌の一覧、解説の文を返します（`machi` の評価と見逃した待ち `missed` は「待ち当て」の節）。解説は、`nanikiru` では `advice.Review` と同じ言い回しにそろえ、「この問題は向聴・有効牌・聴牌時の待ちだけで比べています（守備と打点は考えません）。」と添えます。答えた牌そのもの（赤か否か）で Review を引くので、普通の5を持ったまま赤5を切った答えは、牌種が1位でも不正解です（赤ドラをただ失うため。`best` には普通の5が出ます）。答えが2位の牌なら、1位との比較の文は Review と重なるので足しません。

### 何切る（`nanikiru`）のフィルタと level

| level | 局面 |
|---|---|
| 1 | 1向聴、巡目 4〜9 |
| 2 | 2向聴、巡目 3〜8 |
| 3 | 1〜2向聴、巡目 6〜12、1位と2位の差が有効牌だけ（向聴は同じ） |

どの level でも、1位と2位の差がはっきりした局面だけを出します。

- 向聴で差がつくか、
- 有効牌の差が4枚以上かつ2位の15%以上、または
- 有効牌が同じで、聴牌時の待ちの差が0.5以上（1向聴のとき）。有効牌で負けている牌を待ちで「はっきり上」とは言えないため、有効牌が同じときだけ待ちで比べます。

1位に並ぶ牌種は2種までとします。正解が3種以上ある問題は練習にならないためです。「2位」は1位に並ばない牌のうち最もよいものです。

局面を見始める巡目は、シードと level から level の範囲で決めます（そこから範囲の終わりまでで最初に通った局面を使う）。同じシードでも level ごとに違う局面になりやすくするためです。

切り進めでは、各打牌の分析を一般形の行だけにします。順位1〜3（向聴・有効牌・待ち）はこれだけで決まり、同率の牌は近い役を見ずにドラ・么九・牌順で選びます。役の分析は生成の時間の9割を占めていたためです（下の「性能」）。

### 待ち当て（`machi`）

鳴きのない13枚の聴牌形を見せ、待ちの牌種をすべて答えさせます（`choose` は `"many"`）。

| 論点 | 決定 | 理由 |
|---|---|---|
| 待ちの定義 | その牌種を1枚足すと和了形（一般形・七対子・国士無双）になる牌種すべて。見えている枚数は見ない | 問いは手の形だけ。局面に捨て牌も他家もないので、見えている枚数で待ちを減らすと答えが形から決まらなくなる |
| 4枚使いの牌 | 手が4枚持っている牌種は待ちにしない | 5枚目は引けない（形の上の待ちでも和了できない）。そのため 4枚使いの単騎だけの手は聴牌として出さない |
| 正解 | 答えの牌種の集合が待ちの集合とちょうど同じ | 見逃し・余分のどちらも不正解。赤5は5として数える。同じ牌種を2回答えたら 400 |
| 答えの数 | 1〜9種（`maxWaits`）。待ちが10種以上の手（国士無双十三面）は出さない | 9種は清一色の九面待ちの上限。答えの上限と出題の上限をそろえて、どの問題も正解できるように |
| 局面 | 手牌13枚だけ。`drawn` は null、ドラ表示牌・捨て牌は空、`junme` は 0、`remaining` は手牌を除いた枚数 | 待ちは形だけで決まるので、卓の情報は出さない。`Position` の形は `nanikiru` と同じにそろえる |

| level | 局面 | 作り方 |
|---|---|---|
| 1 | 清一色でない聴牌で、待ちが1〜2種。待ちのすべてを1つの塊（単騎・嵌張・辺張・両面・双碰）が説明する形 | 練習と同じ山で、配牌から「一般形の向聴 → 見えていない有効牌の枚数 → 么九牌 → 牌順」で最善を切り進め、打牌後の13枚が level に合った最初の手 |
| 2 | 清一色でない聴牌で、待ちが3種以上、または1つの塊では説明できない形（延べ単、両面＋単騎、4枚使いで片側が消えた両面など） | level 1 と同じ |
| 3 | 清一色（1つの数牌だけ）の13枚で、待ちが3種以上 | シードの乱数で色を決め、その色の36枚から13枚を引く。聴牌で待ちが3種以上なら採用 |

「1つの塊が説明する」は、待ちのどれかで和了したときの読み（`yaku.Readings`）のうち、和了牌が完成させた塊の待ち（単騎・嵌張・辺張は1種、両面は両側、双碰は2つの対子）が、手の待ちの集合とちょうど同じになるものがあることです。七対子・国士無双の読みは、待ちが1種なら単騎として扱います。

level 1・2 の切り進めは、アドバイスの順位づけ（`nanikiru` の切り進め）ではなく、一般形の向聴と有効牌の枚数だけで選びます。アドバイスを毎巡計算すると level 2 の生成が1問あたり平均 50 ms・最悪 290 ms ほどかかったためです（今の作り方では下の「性能」）。待ちの数で level を分けるので、聴牌の質を左右する順位3（待ちの広さ）は要りません。

解説（`text`）は、正誤（正解。／見逃した待ち: …。／待ちではない牌: …。）、「待ちは 1索・4索・7索 の3種。」、そして待ちごとに和了形の一例を「1索で 123m 456m 11p 123s 456s（両面）」の形で並べます。和了形の例は、その牌での読みのうち最も広い待ちの読み（両面 → 嵌張 → 辺張 → 双碰 → 単騎）を選びます。七対子は「（七対子の単騎）」、国士無双は「国士無双」と書きます。

### 押し引き（`oshihiki`、#241）

| 論点 | 決定 | 理由 |
|---|---|---|
| 局面 | 4席とも普通の CPU（自分の席も）で `source` の配牌から打ち、他家がリーチしている間の自分の打牌のうち、level のフィルタを最初に通ったもの。自分は門前・リーチしていない・ツモ和了できない手番に限る | 実戦で出る形のリーチと河にするため。自分の鳴き・リーチ・和了は問いを変えるので除く |
| 正解 | 手の牌種ごとに、リーチ者それぞれへの `cpu.Danger`（0 安全〜9 無筋の中張牌）を足し、最小に並ぶ牌種すべて | CPU が降りるときと同じ物差し。4段階の `DangerLevel` では同点が多すぎて問いにならない |
| 正解の数 | 最も安全な牌種が2種まで、かつ全部ではない局面だけ | 安全牌だらけの手は問いにならない |
| 解説 | 牌ごとの根拠（`reason`）: 現物・リーチ後に通った牌・筋・ノーチャンス（壁）・筋とノーチャンス・片筋・無筋の端牌／2・8牌／中張牌・字牌の見えている枚数。2人以上のリーチでは「下家に筋、対面に現物」のように席ごと | issue の「根拠を文章で」。危険度の数だけでは読み方が身につかない |
| 押し引き | 押すか降りるかは問わない（自分の手は採点に入れない） | issue の「最初は対象外」 |
| 局面の形 | `Position.seats` に4席の風・リーチ・河（リーチ宣言牌・鳴かれた牌の印）・鳴き。形は対局の `seats` と同じ | ページが対局の河の部品をそのまま使えるように |

| level | リーチ | 最も安全な牌 |
|---|---|---|
| 1 | 1人 | 安全（危険度 0）: 現物か、リーチ後に通った牌 |
| 2 | 1人 | 安全な牌がない: 筋・壁・字牌の見え方で読む |
| 3 | 2〜3人 | どれでも（リーチ者ごとの危険度の和で比べる） |

候補の1局は CPU の対局まるごと（手元で約 6 ms）です。CPU（`cpu.Player`）は問題どうしで1つを使い回し、向聴の memo を温かく保ちます（memo はキャッシュなので打牌は変わりません）。シード 1〜30 で、1問あたり平均 level 1: 14 ms、level 2: 48 ms、level 3: 61 ms、最悪 200 ms ほどでした。2人リーチだけに絞った level は、1局に1度も出ない対局が多く平均 140 ms・最悪 430 ms で、見つからないシードもあったため、level 3 は2人以上のリーチなら安全牌の有無を問いません。

## 要求

```
POST /api/problems         {"kind": "nanikiru", "level": 1, "seed": 42}   → Problem（答えなし）
POST /api/problems/answer  {"id": "nanikiru:1:42", "answer": ["9m"]}     → Result
```

`seed` を省くとランダムに選び、`Problem.seed` で返します。形は `docs/api.md` の「Problems」に書き、TypeScript の型は `web/src/apiTypes.ts` に置きます。

## 性能

`nanikiru` の生成は、山を作り、巡目までアドバイスの最善を切り進めて、巡目ごとにアドバイスを1回計算します。手元（ネイティブ）で、シード 1〜2000 について 1 問あたり平均 2〜4 ms、最悪 35 ms ほどでした（level 1: 平均 3.3 ms・最悪 34 ms、level 2: 2.0 ms・15 ms、level 3: 4.3 ms・32 ms）。採点も同じ生成をもう一度します。テスト（`TestSweep`）は平均が 100 ms を超えたら失敗します。

`machi` の生成は、シード 1〜2000 について手元（ネイティブ）で level 1: 平均 0.9 ms・最悪 7 ms、level 2: 平均 4.9 ms・最悪 40 ms、level 3: 平均 0.06 ms・最悪 0.3 ms でした。候補のシードは最大で level 1: 6 番目、level 2: 53 番目、level 3: 60 番目まで進みました。テスト（`TestMachiSweep`）も平均が 100 ms を超えたら失敗します。

## 画面（#239）

`?mode=quiz&kind=&level=&seed=`（`web/src/quiz/QuizApp.tsx`、ヘッダーのモード「問題」）で、出題 → 回答 → 解説 → 次の問題を回します。

- URL: `kind` は既定 `nanikiru`、`level` は既定 1（知らない値も既定に戻す）。`seed` がない（またはエンジンが受け付けない形の）ときはエンジンが選び、出題後に `history.replaceState` で URL に書くので、再読み込みで同じ問題になります。URL の読み書きは `web/src/quiz/quiz.ts`（`npm test` で単体テスト）。
- 出題: ヘッダーの状態の行に難易度・巡目・場風・自風・成績（正解数 / 回答数、ページを開いている間だけ）とドラ。下に問い（「何を切る？」）と、練習と同じ手牌の欄（`Hand`、ツモ牌は離して表示、捨て牌つき）。
- 回答: `choose: "one"` の問題は手牌の牌で答えます。練習の打牌と同じく、マウス・キーボードは1回のクリック（Enter）で、タッチは1回目のタップで選び、同じ牌の2回目で答えます（タッチかどうかは `pointerdown` で決める。iOS は click の `pointerType` を `mouse` と報告するため）。
- 採点: 正解・不正解のバッジ、正解の牌、`text` の解説、切る牌ごとの順位の表（順位・向聴・有効牌、1向聴の問題があれば待ち。1位の行を強調し、自分の答えの行は太字と「あなた」）。手牌では正解の牌を持ち上げて（`.tile-advice`）、不正解の答えを赤枠（`.tile-quiz-wrong`）で示し、それ以上は答えられません。「次の問題」は同じ種類・難易度で `seed + 1`。
- 難易度は「設定」のラジオ（1向聴・2向聴・上級）で、選ぶとすぐ同じシードのその難易度の問題になります。
- 種類は「設定」のラジオ（何切る・待ち当て・押し引き）で、選ぶとすぐ同じシードのその種類の level 1 の問題になります。
- 待ち当て（`machi`、`choose: "many"`、#242）: 手牌は答えに使わず（押せない）、その下の牌の一覧（`QuizPicker`、34種を萬子・筒子・索子・字牌の4行）から待ちを選びます。各牌は押すたびに選ぶ・外す（`aria-pressed`）で、「答える」で送ります（9種まで、`MAX_PICKS`）。局面に巡目・風・ドラがないので、ヘッダーの状態の行は難易度と成績だけです。採点では一覧の上で待ちを持ち上げ（見逃した待ちも）、待ちでない答えを赤枠にし、順位の表の代わりに待ちごとの残り枚数と、答えに入れたか（選んだ／見逃し）の表を出します。難易度の名前は 基本形・複合形・清一色。
- 押し引き（`oshihiki`、#241）: 問いの下に他家の河（`QuizTable`、下家・対面・上家の行に、席の名前とリーチのバッジ、対局と同じ `River`（リーチ宣言牌は横向き）と `Melds`）。答え方は何切ると同じ。採点の表は 順位・打牌・根拠（`reason`、折り返す）・危険度。採点は牌種で決まるので、手牌の印も牌種で付けます（赤5も普通の5と同じ）。難易度の名前は 現物あり・現物なし・複数リーチ。
- 種類を足すときは、見出しと問いを `quiz.ts` の `KINDS`、難易度の名前を `LEVEL_NAMES` に足します。道場では、秘伝の課題が `kind`・`level` と問題数を決めて、この画面を開きます。
